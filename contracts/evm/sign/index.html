1b. UptimePool v2 (community pools) — 1 transaction

CREATE2 through 0x4e59…956C, same calldata as script/DeployUptimePoolV2.s.sol. Anyone can back a pool, each backer withdraws only their own pro-rata share. v1 keeps running: the app switches only when UPTIME_POOL_V2_BRADBURY is set to the address below.

Admin and rotationDelay are permanent. Spender changes take rotationDelay (48 hours minimum, enforced by the contract) from proposeSpender to executeSpender, both sent by the admin Safe. The scheduler and mailer below are set by the constructor, right now, with no wait: this is the only time that is possible, so set both. Admin, scheduler and mailer must be three different addresses.

3. Set mailer on a deployed UptimePool — 2 transactions

For a pool whose admin is the connected wallet (v1, or the first v2). proposeSpender(2, mailer), then executeSpender(2) once rotationDelay has passed (0 on v1, so right away). The mailer must differ from the scheduler (SpenderHasRole). Only the address goes on chain; its key stays in 1Password. A pool whose admin is a Safe cannot be changed from here: those two calls have to be Safe transactions.
